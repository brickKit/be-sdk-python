# authz 协议：JWT + Bundle 权限判定协议

## 这份文档是什么

这份文档独立描述 `be-sdk-go`/`be-sdk-python`/`be-sdk-ts` 三份 SDK 共同实现的一套权限判定协议——一个 HTTP/gRPC 服务如何在本地判断"这个请求有没有权限"，不需要每次请求都同步问一个中心授权服务器。

不假设读者知道 brickKit 平台是什么、也不假设读者用的是这个项目——只假设你要做以下三件事之一：

1. 直接用这几个 SDK 之一（在别的项目里）；
2. 实现一个与之兼容的授权服务（替代下文举例的 `infra-authz`）；
3. 用另一种语言重新实现一份兼容的判定逻辑。

这不是一个自造协议——它是 [OPA](https://www.openpolicyagent.org/)（Open Policy Agent，CNCF 毕业项目）"策略下发到本地、本地决策"这套标准形态的一个简化版本，判定是进程内存里的一次 map 查找，零网络往返。

## 整体模型

两个独立的输入源：

1. **身份**——由 JWT 提供，RS256 签名，验签用标准 JWKS 端点，本地完成（不向签发方发起同步调用）。
2. **策略**——由一个 "bundle" 端点提供，本地进程每 15 秒轮询一次、缓存在内存里，判定时纯本地查找。

身份和策略是两条完全独立的信息通道，互不依赖对方的实现细节——你可以只换掉签发身份的那一半（比如换一个 OIDC 提供方），策略服务不用动一行；反过来也一样。

## 1. 身份：JWT

### 1.1 期望的 Claims

标准 claims：

| Claim | 类型 | 说明 |
|---|---|---|
| `sub` | string | 用户唯一标识，必须存在 |
| `iat` | number（Unix 秒） | 签发时间，必须存在 |

自定义 claims：

| Claim | 类型 | 说明 |
|---|---|---|
| `roles` | string[] | 这个人当前持有的角色代码原始集合（未展开成权限键） |
| `dept_path` | string | 物化路径，如 `/1/12/`——每一段是祖先部门的 id（含自身）。空字符串表示"没有具体部门归属"（如坐在组织树根节点） |
| `org_id` | string | 法人/租户标识（多租户场景用；单租户部署可以是一个固定值） |

### 1.2 验签

- 算法固定为 **RS256**，公钥来自一个标准 JWKS 端点（`GET` 一个 URL，返回 [RFC 7517](https://www.rfc-editor.org/rfc/rfc7517) 格式的 JSON Web Key Set）。
- 三份 SDK 都显式只信 RS256——即使底层库本身已经拒绝 `alg: none`，仍然显式白名单，这是纵深防御，不是多此一举。
- JWKS 有本地缓存，不是每次验签都重新拉取；缓存失效或找不到匹配的 `kid` 时才重新拉取。

### 1.3 谁签发这个 JWT

协议本身不关心谁签发——任何 OIDC/JWT 签发方都可以，只要它：

1. 用 RS256 签名，公钥能通过一个 JWKS 端点拿到；
2. claims 里带上 `sub`/`iat`/`roles`/`dept_path`/`org_id`（后三个是自定义 claims，签发方需要知道去哪查这些值——这正是"身份服务"要和"策略服务"对接的地方：谁来算一个 `sub` 对应的 `roles`/`dept_path`/`org_id`，是实现细节，不属于本协议）。

## 2. 策略：Bundle

### 2.1 端点

一个 HTTP `GET` 端点（下文举例的实现里路径是 `/authz/bundle`），返回：

```json
{
  "roles": {
    "sales_rep": ["erp.sales.view", "erp.sales.create"],
    "sales_manager": ["erp.sales.view", "erp.sales.create", "erp.sales.confirm"]
  },
  "stale_since": {
    "u_zhangsan": 1788904504
  }
}
```

- **`roles`**：角色代码 → 权限键数组。**纯并集语义，没有 Deny**——一个人拿到的有效权限，是他持有的全部角色对应权限键集合的并集，不存在"某个角色反而减少权限"这种情况。
- **`stale_since`**：`sub` → Unix 秒时间戳的**有界**列表，只包含"最近发生了会让已签发 token 失效的事情"（授予/撤销角色、踢人、角色到期）的人。**不在这个表里的人永远不 stale**——这个表被设计成有界的：只需要覆盖"最近 2× access token 有效期"这个滚动窗口，不需要、也不该保存全部历史记录。

### 2.2 轮询与缓存

- 客户端（SDK）每 **15 秒**做一次条件 GET（带 `If-None-Match` 请求头），服务端未变化时回 `304`，客户端沿用内存里已有的内容，不重新解析。
- 单次拉取失败（网络问题、服务重启）**不清空已有数据**——继续用内存里最后一次成功拉到的内容判定，直到下一次轮询成功为止。这是刻意的 **fail-static** 设计：策略服务的一次抖动，不该让所有依赖它判权限的服务同时拒绝掉所有请求。
- "进程从启动到现在一次都没有成功拉取过 bundle" 是需要单独识别的一种状态（见下面判定链的第 7 步）——它和"拉取成功过、只是这个角色恰好没有这条权限"是两回事，前者是"暂时不知道"，后者是"确定没有"。

### 2.3 谁提供这个端点

同样，协议不关心谁提供——任何服务都可以，只要它按上面的 JSON 形状响应、支持 `If-None-Match`/`304` 这套条件请求。

## 3. 判定链

给定一个请求要求的权限键 `perm`（或两个约定的哨兵值之一，见下），判定按顺序进行：

1. **`perm` 是"公开"哨兵值**（约定为空字符串）→ 直接放行，不验签、不查 bundle。这是显式的"这个接口公开"标记，故意不用"省略参数"表达同样的意思，避免"忘了传权限键"这种失败模式在类型系统/静态扫描层面被漏过。
2. **验签基础设施还没就绪**（没有配置 JWKS 地址，或配置了但初始化失败，比如地址本身不合法）→ 非"公开"的请求一律拒绝（403）。这是"整个授权链路还没接上"时的默认状态——安全机制的默认值只能是拒绝，不能是放行。
3. **请求没带 `Authorization: Bearer <token>`，或格式不对** → 401。
4. **验签失败**（签名不对、token 已过期、缺少必填 claim）→ 401。
5. **`jwt.iat < stale_since[sub] − 时钟偏差余量`** → 401，响应头带 `WWW-Authenticate: Bearer error="token_stale"`。时钟偏差余量取 5 秒，用来消掉机器间的毫秒级时钟不同步造成的误判。
6. **`perm` 是"已登录"哨兵值**（约定值，不是空字符串，两个哨兵值必须能区分开）→ 验签通过且不 stale 就放行，不查具体权限键。用于"任何登录用户都该能访问，但不对应某个具体业务权限"的端点（比如"查询我自己当前的权限列表"这类接口）。
7. **策略服务从启动到现在一次都没拉取成功过** → 503（不是 403）。区分这两种状态是刻意的：503 说的是"我们现在还不知道"，客户端/网关应该按"稍后重试"处理；403 说的是"已经查过了，确定没有"，重试没有意义。
8. **展开 `jwt.roles[]` 对应的权限键并集，`perm` 不在其中** → 403。
9. 其余情况 → 放行，同时把验签得到的身份信息（`sub`/`dept_path`）换算成下面第 4 节的 `ScopeFilter`，供业务逻辑做行级数据过滤用。

## 4. 数据范围：ScopeFilter

判定链第 9 步放行之后，会算出一个结构体（三份 SDK 里字段名一致，只是各语言的大小写习惯不同）：

| 字段 | 来源 | 用途 |
|---|---|---|
| `all` | `dept_path == ""` | 是否不限——坐在组织树根节点的人天然为真，不是特判出来的 |
| `prefix` | `dept_path` | 前缀匹配，"本部门及下级"：`WHERE dept_path LIKE prefix \|\| '%'` |
| `exact` | `dept_path` | 精确匹配，"仅本部门"：`WHERE dept_path = exact` |
| `owner` | `sub` | 精确匹配，"仅本人"：`WHERE owner_id = owner` |
| `in` | 不由本协议提供 | 保留给"自定义列表"场景，见 §4.1 |

⚠️ 这是一个**纯函数的输出**：`all`/`prefix`/`exact`/`owner` 这四个字段**永远**从同一份已验签 JWT 的字段填，不由判定逻辑自己判断"这次该用哪一档"——用哪个字段做过滤，是调用方（某一条具体的查询/接口）的静态选择，判定逻辑本身不参与、也不知道这个决策。

⚠️ **有一条容易被反方向实现的 SQL 约定，需要显式说明**：这个协议下，**空字符串表示"不限"**（`WHERE dept_path LIKE '' || '%'` 等价于匹配一切）。这意味着：如果某个实现在"取不到已验签的身份信息"这种情况下，选择返回这个结构体的**零值**（各字符串字段皆为空字符串）而不是报错，效果会被下游 SQL 解读成"放行一切"——方向是反的（fail-*open*，而不是 fail-*closed*）。正确的实现是：取不到已验签身份时必须抛异常/panic，让这种编程错误在开发/联调阶段就暴露出来，而不是安静地多返回几行本不该被看到的数据。

### 4.1 "自定义列表"这一档不在本协议范围内

如果业务需要"这个人只能访问 A、B 两个仓库"这类、过滤值不来自 JWT 而来自业务自己数据的维度，本协议**不提供**这类机制——`in` 字段是刻意留空的。理由：

- 这类"谁能访问哪个 X"的分配数据（X 是仓库、法人、项目……）通常是**业务概念**，不建议塞进 JWT——那会让"身份"和"业务数据"的边界变模糊，也会让 JWT 随着这类维度增多而膨胀。
- 也不建议由本协议描述的策略服务（bundle 端点）代管——bundle 端点管的是"角色 → 权限键"，不是任意维度的任意值列表，混在一起会让这个服务的职责边界变得不清楚。

实现方式：由持有这份业务数据的服务自己维护一张"`sub` → 允许访问的值列表"的表，判定时自己查、自己拼 `WHERE` 条件（`column = ANY(allowed_list)` 是一个常见形状），与本协议给出的四个标准字段并列使用，互不冲突。空列表在这种形状下天然表示"这个人没有被分配任何值，因此什么都看不到"——不需要为空列表单独写一条"是不是要放行一切"的特判分支。

## 5. 本仓库（`be-sdk-python`）的对照

| 协议部分 | 文件 |
|---|---|
| 身份（JWT 验签） | `besdk/jwt_verify.py` |
| 策略（bundle 轮询） | `besdk/bundle.py` |
| 判定链 | `besdk/authz.py` 的 `require_permission` |
| ScopeFilter | `besdk/scope.py` 的 `scope_of` |

公开 API 的具体调用方式（`besdk.get/post/...`、`besdk.require_permission`、`besdk.scope_of`）见仓库根 `README.md`。

姊妹实现：`be-sdk-go`、`be-sdk-ts`——同一份协议的另外两种语言实现，字段名/判定语义逐字对应，只是各自语言的调用习惯不同（`be-sdk-ts` 因为 GraphQL 没有路由只有字段，判定的应用颗粒度不同，见它自己那份文档的对应小节）。

## 6. 兼容性

这份协议目前没有独立的版本号——文档发布时，三份 SDK 由同一个项目同步维护，靠"三份实现互相走读一遍、确认逐字对应"来保证一致，还没有走到需要单独给这份协议本身版本化的阶段。如果这份协议未来要脱离当前维护它的项目、被更多独立方实现或消费，建议：

- 给这份文档本身一个版本号；
- 任何破坏性变更（新增必填 claim、修改 bundle 的 JSON 形状、修改判定链的步骤顺序或语义）需要一次协调好的、跨全部实现方的主版本号升级；
- 新增可选字段、新增哨兵值这类纯增量变更可以不升主版本号。
